# Heap Sort

**Difficulty:** intermediate · **Category:** sorting

Heap sort runs in two phases:

1. **Build a max-heap** in place over the whole array. After this, the largest value sits at index
   $0$ and every parent dominates its two children.
2. **Repeatedly extract the max.** Swap the root with the last element of the heap, shrink the heap
   by one, and sift the new root down to restore the heap property. Each extraction parks one
   value in its final sorted position at the end of the array.

## What you're seeing

- The **dashed bracket** marks the current heap region. It starts as the whole array and shrinks
  by one with every extraction. Bars to the right of the bracket are already in their final
  sorted position.
- **Yellow** bars are being _compared_ — a parent against one of its two children during sift-down.
- **Blue** bars (with a tick mark) just _swapped_ during sift-down, or during the root-to-end
  extraction move.
- **Green** bars are in their _final sorted position_ once the algorithm finishes.

The first batch of compares (with the bracket spanning the whole array) is the heap-build phase.
After that, every subsequent shrink of the bracket corresponds to one extracted maximum being
placed at the boundary.

## Why is the heap structure stored as an array?

A binary heap is conceptually a tree, but you can store it implicitly: for the node at index $i$,

- its **left child** is at index $2i + 1$,
- its **right child** is at index $2i + 2$,
- its **parent** is at index $\lfloor (i - 1) / 2 \rfloor$.

No pointers, no allocations — just arithmetic on indices. This is what makes heap sort _in place_:
the heap and the array are the same memory.

## Why is it $O(n \log n)$?

- **Build-heap takes $O(n)$.** It feels like it should be $O(n \log n)$ because there are $n/2$
  internal nodes and each sift-down is up to $\log_2 n$ work — but a tighter analysis shows the
  total work is bounded by a geometric sum that converges to $O(n)$.
- **Each extract-max takes $O(\log n)$.** We swap the root to the back, then sift the new root
  down through at most $\log_2 n$ levels. We do this $n - 1$ times.

Total: $O(n) + O(n \log n) = O(n \log n)$.

## Heap sort vs. quick sort vs. merge sort

| Algorithm  | Avg time      | Worst time    | Space           | Stable |
| ---------- | ------------- | ------------- | --------------- | ------ |
| Heap sort  | $O(n \log n)$ | $O(n \log n)$ | $O(1)$          | No     |
| Quick sort | $O(n \log n)$ | $O(n^2)$      | $O(\log n)$ avg | No     |
| Merge sort | $O(n \log n)$ | $O(n \log n)$ | $O(n)$          | Yes    |

Heap sort is the only one of the three with both **guaranteed** $O(n \log n)$ time _and_ $O(1)$
extra space. The catch is its constant factor: cache behavior is poor because sift-down jumps
through the array by powers of two, so on real machines a tuned quicksort usually wins on random
data despite its worse asymptotic worst case.

Heap sort shines when:

- You need a guaranteed worst-case bound (real-time systems, security-sensitive code where input
  may be adversarial).
- Memory is genuinely tight and merge sort's auxiliary array isn't free.
- You already have a heap around for some other reason — at which point the sort is almost free.
